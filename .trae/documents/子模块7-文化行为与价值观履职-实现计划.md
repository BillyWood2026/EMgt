# 子模块7 文化行为与价值观履职（behavior 包）实现计划

## Context
按 ccms_spec 需求规格推进 CCMS 企业文化管理模块。子模块1-6 已完成（foundation/case/activity/honor/training/survey）。本子模块对标华为价值观考核体系，落地员工文化行为举证、负向行为稽核、干部履职、价值观评议、个人文化积分台账五大能力。核心算法为「员工文化综合得分」（客户导向25% + 奋斗担当30% + 艰苦奋斗25% + 自我批判20%）与「部门文化达标率」。

复用既有骨架：`common/cul`（CulRole/CulBizException/AuditService/CurrentHeader）+ casehub 的三级审批/积分样板 + survey 的 @JsonFormat/parseQuestions 教训 + honor 的 browser_use 子代理防虚报流程。

### 错误码 `E-BH`
- `01` 字段校验（长度/枚举/范围/附件<1/自评分越界/维度非法）
- `02` 状态机非法
- `03` 驳回/审核意见不足5字
- `04` 权限归属拦截（非本人/非下属/非干部/非文化岗）
- `05` 提交完整性缺失
- `06` 重复提交（同人同期在途 / 同 config 同对同人重复评议）
- `07` 时间窗非法（评议窗口外 / 发生时间在未来）
- `08` 红线条款不存在或不匹配
- `09` 整改期限非法（在过去 / 超今+180天）
- `10` 评议权重合计≠100
- `11` 评议配置已发布不可改 / 已结束
- `12` 隐私越权（员工看他人 / 跨部门）
- `13` 积分入账失败/重复入账
- `14` 履职5项不齐 / 周期格式非法
- `15` 申诉超7天 / 状态非已告知

### 各 Service 核心方法（鉴权点标注）

**EvidenceService**
- `mine()` 全员看自己 / `todoList()` C04(stage=1 下属)+C02/C03(stage=2) / `adminList()` CULTURE_STAFF / `get(id)` 本人或文化岗或 C04（下属）否则 E-BH-12
- `save(e)` C01 本人，仅草稿可改，校验 E-BH-01/07
- `submit(id)` 本人，草稿→待初审
- `approve(id, pass, opinion)` stage=1: C04+C99（且是 contributor 的 dept 主管）；stage=2: C02/C03/C99。驳回 opinion≥5字（E-BH-03）；**stage=2 通过 → 调 ScoreService.bookFromEvidence() 入账 → 回写 point_txn_id + final_score + 状态=已入账**

**BehaviorAuditService**
- `adminList(status, dept, targetUser)` CULTURE_STAFF + C04（仅本部门）/ `myAudit()` C01 看自己 / `get(id)` 本人/登记人/文化岗/高管否则 E-BH-12
- `create(a)` C02/C03/C04/C99；redlineCode 非空校验 cul_redline 存在并联动 deduct 标准（E-BH-08）；状态=已登记→自动 notify()→已告知
- `confirm(id)` targetUser 本人；已告知→已确认（E-BH-02）
- `appeal(id, reason)` targetUser；已告知→申诉中；reason≥10字；告知后7天内（E-BH-15）
- `verdictAppeal(id, uphold, opinion)` C03/C07/C99；uphold→整改实施中；false→申诉驳回已归档
- `submitRectify(id, note, evidenceJson)` targetUser；已确认/整改实施中→待验收；佐证≥1
- `accept(id, pass, opinion)` C04+C99 主管或 CULTURE_STAFF；通过→扣分生效（调 ScoreService.bookFromAudit()）；驳回→整改实施中

**DutyService**
- `mine()` C04 自己 / `todoList()` 上级（C03/C07）看待审核 / `adminList(status, period, dept)` CULTURE_STAFF/C07
- `save(d)` C04；dutyItems 必5项（E-BH-14）；同 officer+period 在途拦截（E-BH-06）
- `submit(id)` C04 本人；草稿→待审核
- `review(id, pass, opinion)` C03/C07/C99；驳回≥5字

**ReviewService**
- 后台：`configList(status)` / `saveConfig(c)` 校验 weight 合计=100（E-BH-10） / `publishConfig(id)` 校验时间窗（E-BH-11） / `finishConfig(id)`
- 前台：`myTodo()`（按 targetScope 内） / `myGiven()` / `myReceived()`（仅本人+文化岗+C07）
- `submitReview(r)` 窗口内 / 同 config_id 同人同 relation 拦截（E-BH-06）；服务端算 totalScore+levelTag（算法71）；落库后模拟 pushToPerf() 置 pushed=1

**算法71**（私有静态）：
```java
static double calcTotal(double customer, double strive, double hardship, double reflect)
   = customer*0.25 + strive*0.30 + hardship*0.25 + reflect*0.20
static String levelOf(double t)  // S≥95 / A 85-94.9 / B 70-84.9 / C 60-69.9 / D<60
```

**ScoreService**（积分核心，被 Evidence/Audit/Review 三方依赖）
- `myAccount()` C01 仅自己（E-BH-12）/ `accountOf(userName)` C04 仅本部门、C02/C03/C07/C99 全员 / `deptList(dept)` / `txnList(userName, dimension, periodTag)` / `rankList(period, scope)`（按 total 倒序，同分按 neg_count 升序）/ `deptCompliance(dept, periodTag)` 算法72
- `@Transactional bookFromEvidence(e)` 加分 / `bookFromAudit(a)` 减分 / `bookFromReview(r)` 评议推送绩效时同步影响
- `ensureAccount(userName, dept)` 不存在则建，基线 60
- **幂等**：txn 表 `(source_type, source_id, direction)` selectCount 拦截重复入账（E-BH-13）

**算法72**：部门达标率 = 部门得分≥70人数 ÷ 部门总人数 ×100%（≥70 含 70，分母是部门总人数非评议完成人数，结果保留2位小数）

## 风险与坑（结合历史经验）

1. **@JsonFormat 全字段必加**（survey 教训）：所有 LocalDateTime/LocalDate 必须显式标注
2. **browser_use 子代理虚报**：每步操作后必须 mysql 落库 + cul_audit_log 审计表双验证
3. **冒烟脚本 UTF-8 BOM + PS 函数名坑**：避开 `H`/`$pid`；中文 POST body 用 `[Text.Encoding]::UTF8.GetBytes($json)`；中文 GET 参数 `[uri]::EscapeDataString()`；开头先清理 `LIKE 'smoke-%' / 'SMOKE%'`
4. **mysql 管道中文乱码**：`Get-Content -Raw -Encoding UTF8 | mysql --default-character-set=utf8mb4`；清理条件用 ASCII
5. **UNIQUE 索引坑**（case 教训）：`user_name`/`evidence_no`/`audit_no` 不要建 UNIQUE，用普通 KEY+应用层拦截
6. **维度枚举逐字对齐**（training 教训）：前后端、种子、算法71 权重 JSON key、数据库 VARCHAR 全部一致
7. **BehaviorAuditService 命名**：避免与 `common.cul.AuditService` 冲突
8. **积分幂等**：记账前必查 `cul_behavior_score_txn` 同 (source_type, source_id) 是否已入账
9. **「员工间禁止互查」硬约束**：服务端校验，不依赖前端隐藏（E-BH-12 核心场景）
10. **驳回意见 ≥5 字**：前端+后端双重校验，写入 `reject_reason`+`approval_log` 双处
11. **算法71 一位小数**：`BigDecimal.setScale(1, HALF_UP)` 避免浮点误差
12. **数据库清理顺序**：先删 `cul_behavior_score_txn` 再删 `cul_behavior_score_account` 再删父单据

## 验证方案

### 冒烟脚本 `smoke_behavior.ps1`（可重入，目标 ~50 断言全绿）

**A. 状态机**（happy-path + 各驳回分支）
1. 举证：建草稿→提交→C04 初审驳回（意见≥5字）→状态回草稿→重新提交→C04 通过→C03 复核通过→final_score 写入+积分账户增加+流水+point_txn_id 回写+状态=已入账
2. 稽核：C03 登记（不挂红线）→已告知→员工确认→整改实施→主管验收通过→扣分生效；另一条：员工申诉→C03 申诉驳回→归档
3. 履职：C04 提交→C03 审核驳回（≥5字）→重填→通过归档
4. 评议：C03 建配置（权重 25/30/25/20）→发布→上级评下级→断言 totalScore 与算法71 一致+level 正确+pushed=1

**B. 权限**
- C01 越权访问他人 `/score/{other}` → 400/403 E-BH-12
- C01 调 `/audit` 登记接口 → 403
- C04 跨部门访问他人证据 → 403
- 员工试图复核自己举证 → 拦截

**C. 积分算法**
- 算法71：构造 (90, 95, 85, 80) 验证 total=88.25→A 级
- 算法72：种子部门 5 人，3 人≥70 → 达标率 60%
- 等级边界：95.0 是 S，94.99 是 A；70 是 B 下限，<60 是 D

**D. 隐私隔离**
- `/score/myAccount` 不带参数返回 X-User-Id 本人
- `/evidence/mine` 不返回他人
- `/audit/myAudit` 仅本人
- 高管 `/score/deptList` 不带部门过滤可看全员

**E. 驳回意见必填**：各 approve 接口 pass=false 且 opinion<5 字 → 400 E-BH-03

**F. 幂等**：同一证据复核接口重复调用 → 第二次 E-BH-02 且不重复入账

**清理**：每轮跑完软删 smoke 数据 + 审计清理
